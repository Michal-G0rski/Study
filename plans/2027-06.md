# June 2027 — Stage 2, SC-200 Exam & Attack-Chain Lab Begins

Month 9 of [the plan](../README.md). **15 h/week: 2.5 h/day, Monday to Saturday, Sunday off.**

Three weeks, 45 hours. No public holidays land on a study day this month. The first two weeks finish the exam-prep block that started in [May](2027-05.md) and sit the SC-200 exam; the third opens the **endpoint & AD attack-chain lab** — the flagship, and the last major piece of Stage 2 before the [checkpoint](../README.md#employability-checkpoint--month-11) in August.

> **Why the flagship changed.** The old plan's flagship was a web app you attacked with SQLi/XSS and detected — an *AppSec* exercise. An L1 SOC analyst does not live in web-app logs; they live in endpoint, identity and email telemetry. So the flagship is now an intrusion chain against a Windows/AD lab, emulated with real attacker technique-runners and detected in the exact telemetry a SOC seat reads — Sysmon, Windows Security, and your Feb–March detection library. It continues December's Sysmon work and January's AD attacks directly, instead of opening a new AppSec front you would never staff in the target role.

## Week 3 — 21 to 26 June

The attack-chain lab begins.

Split: all on standing up the lab and confirming the telemetry pipeline before any attack runs.

Day | Work through
:-- | :--
Mon 21 | Bring the lab up: the December Windows VM running with Sysmon (SwiftOnSecurity config) and the Wazuh agent reporting. Confirm Windows Security + Sysmon events land in the Wazuh indexer. If the chain needs domain events (Kerberoasting, DCSync), decide now: stand up the minimal DC, or plan to replay those links from the January datasets.
Tue 22 | Build the **second** telemetry path, and be honest about its shape: there is no free *live* stream from a home VM into the free ADX cluster — continuous ingestion (Event Hub) is a paid Azure resource — so the path is **batch, per run**. Turn on Wazuh's full event archive on the manager (`logall_json`: every event it receives, not only the ones that raise alerts), cut the archive to the time window of a run, and upload that slice through the cluster's *Get data* wizard as a local JSON file into one table. Script the cut-and-upload once today; next month it runs after every technique. The payoff: ADX and Wazuh then hold **the same events from the same collector**, which is what makes July's engine comparison fair. Write down the field names the archive actually uses (`data.win.system.eventID`, `data.win.eventdata.commandLine`, `…image`, …) — July's KQL and the Sigma field mapping both key on them. A detection you can only test in one engine is half the deliverable.
Wed 23 | **On this lab VM only** — never on the machine you actually use — switch Microsoft Defender's **Tamper Protection off first** (while it is on, the next change silently reverts), then **real-time protection** off. Skip this and Defender quarantines Atomic Red Team's payloads before a single technique runs, and July's attack log fills with "blocked". Then install [Atomic Red Team](https://github.com/redcanaryco/atomic-red-team) (and, optionally, Caldera), and download the prerequisites of every technique in the Friday 18 chain while the VM still has internet. Then **cut the lab to its own VM network** (host-only / internal): the lab VM, the DC if there is one, and the Wazuh manager reach each other; nothing in the lab reaches your home LAN or the internet. Credential dumping and lateral movement stay inside the lab. Finally run one harmless atomic (e.g. a T1059.001 test) end to end and **find it in both engines** — Wazuh live, ADX after the upload — which proves the pipeline before the real chain, not during it.
Thu 24 | Capture a **baseline of normal activity**: an hour or two of ordinary use (logons, admin tasks, file work — what the lab network allows) logged clean, and uploaded to ADX as its own slice the same way as Tuesday's. This is what next month's detections get tuned against for false positives, in both engines — without it, "it fired on the attack" means nothing.
Fri 25 | Write the lab's instrument-and-scope document: host inventory, log sources and their fields, the ATT&CK chain from Friday 18, and the detection-coverage map (which links you already have a rule for, which are new).
Sat 26 | Consolidate: what runs, what logs cleanly into both engines, and exactly what July week 1 must finish before the attack begins.

## Rules for a week that goes wrong

- **The exam week is the exam week.** Do not schedule practice or reading into it as a hedge. Two half-done things is the failure mode here.
- **If the exam is failed, it is failed and rebooked, and the plan does not change.** The [checkpoint](../README.md#employability-checkpoint--month-11) leans on the certificate, but it stands on the incident reports and the detection library just as much. A retake costs days, not the month — and a second full exam fee, which is why May's practice assessments are not optional.
- **The lab stand-up starts on schedule regardless of the exam result.** Waiting for a retake to build confidence first just shortens the work later.
- **Prove the pipeline before the attack, not during it.** If a test atomic doesn't show up in both Wazuh and ADX this week, that is a week-3 problem to fix now — debugging ingestion while you are also trying to attack and detect is the failure mode.
- **Defender stays off only on the lab VM, and the lab stays off your network.** Both go together: an unprotected Windows box running credential-dumping tools belongs on an isolated VM network, nowhere else.
